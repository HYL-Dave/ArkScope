In `browser-third/zh-Hant-1280-catalog.png`, the bottom pagination visibly renders both arrows outside the empty button rectangles; the same displacement is visible in `browser-third/en-390-facts.png`. This is attributable to the new selector, not a pre-existing Button warning or a backend failure. Limit the rule to the page-counter span, for example `.sec-pagination > span` or a dedicated counter class, without changing the shared Button. Add a focused selector regression and have the parent verify that each arrow's bounding rectangle lies within its button in both locales/viewports. Passing click-by-role workflows do not catch this visual defect.

## Minor

- **M1: Query response types omit the legitimate null-data unavailable envelope.** `apps/arkscope-web/src/api.ts:1114` declares envelope `data: T`, and the new `getSecResearchFilings` / `getSecResearchFacts` helpers instantiate it with arrays only. However, `src/api/routes/sec_research.py:34` returns `data: None` for unavailable responses, including `_stored_query` at `sec_research.py:134`. The panel's `page?.data ?? []` already handles this safely, so this is not a demonstrated runtime regression. Make the query return types (and panel Page alias) admit null, or use a status-discriminated envelope, and add an unavailable-null fixture: the new panel state test currently uses `envelope(state)` with its default empty array. This keeps future consumers from trusting an array contract the server does not provide.

- **M2: Hash-first columns make the mobile facts table uninformative at its initial horizontal position.** `apps/arkscope-web/src/settings/SecResearchPanel.tsx:90` puts `fact_id` before namespace, concept, reported value, unit, and period. With max-content/nowrap table sizing at `apps/arkscope-web/src/settings/secResearch.css:35`, `browser-third/en-390-facts.png` shows a long vertical list consisting solely of clipped `secfact_...` hashes; the meaningful fields are all offscreen. The scroll container at `secResearch.css:34` also has no height cap, so pagination and the horizontal scrollbar follow the entire 40-row page. This is a concrete usability issue, but not missing data or a backend defect: the brief explicitly permits horizontal scrolling, so column priority and a height cap are nonblocking improvements rather than newly invented release requirements. Put concept/value/unit/end first and opaque IDs last, retaining exact full values and IDs; consider a bounded max-height with internal scrolling to keep navigation reachable. Apply the same human-readable-first principle to catalog columns if adjusted. No cards or redesign are needed. Verify column order and inspect the resulting 390px first table view with realistic full-length IDs.

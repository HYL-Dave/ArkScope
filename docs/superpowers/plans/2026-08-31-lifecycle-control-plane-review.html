§ 2

The defect register

Severity is by consequence, not novelty. Every entry is confirmed: reproduced by running code, with the decisive output shown.

F1BlockingConfirmed fact_kernel.py:648

A 33-link predecessor chain wedges the run forever — and blocks orphan reclamation for every other case

_MAX_PREDECESSOR_CHAIN = 32. _attempt_chain raises on the 33rd link, and both paths that can rescue a running row route through it unconditionally — fail_run (:2624) and reconcile_running_runs (:2559), each via _automatic_retry_for_failure. The worker swallows both raises.

reproduced

*** fail_run RAISED at chain depth 33: ValueError(automation_predecessor_chain_limit)
rows left status='running' = 1
*** reconcile_running_runs RAISED: ValueError(automation_predecessor_chain_limit)
--- CROSS-CASE blast radius: a second, healthy case
healthy case2 row: before=running after=running  -> STILL STUCK (collateral damage)

Two aggravating facts found while verifying:

  1. Cross-case blast radius. The reconcile loop is not per-row guarded and runs in one _immediate_transaction. With execution_owner_id=None — the startup and per-tick call — the owner continue never fires, so the chain walk runs for every running row. One poisoned row withholds reclamation from all of them.
  2. Reachability is worse than a failure loop. A link is appended whenever the previous attempt is terminal — {failed, blocked, succeeded} — so fully successful runs chain too (verified to depth 33 using only succeeded rows). allow_new_attempt=True is set unconditionally for the per-case Run button, and nothing anywhere prunes the chain. About 32 clicks on one case with an unchanged fingerprint suffices.
Fix directionGet the chain walk off the recovery path — bound the derivation and treat an over-long chain as “retries exhausted”, or catch the two chain errors at the fail_run/reconcile boundary and degrade to a typed terminal state. Independently, reconcile_running_runs must be per-row fault-isolated so one row can never starve the rest.
F2MajorConfirmed data_scheduler.py:1505

A startup fallback poisons the lifecycle telemetry row permanently

There are two calls to reconcile_interrupted_running. Line 1486 passes excluded_sources=("security_lifecycle.automation",); line 1505 does not. That exclusion exists precisely because the lifecycle source's last_result carries a different blob shape.

reproduced

_state_envelope(foreign blob)               *** RAISED ValueError(automation_scheduler_state)
_state_envelope(well-formed lifecycle blob) OK

The consequence is permanent, and the ordering is what makes it so: _load_active_incident runs at :2892, before _write_automation_state at :2945, and its raise is caught at :2953 with a rollback. So the write that would repair the row never executes, and every later record call returns False. The not_installed early return writes only last_status, so it does not clear last_result either. Nothing in-product recovers it.

Reachability is gated — line 1505 needs both the lifecycle reconcile and its failure telemetry to raise. Low probability, permanent consequence, two-line fix.

Fix directionPass the same excluded_sources at line 1505. Separately, let _load_active_incident treat a foreign blob as “no prior incident” rather than raising, so a poisoned row self-heals on the next write.

F4MajorConfirmedMerge blocker automation_scheduler.py:2295

_case_failure_marker classifies recovery as "finalization" only when a finalization-failure record exists; otherwise "new_attempt". But recovery for a succeeded + pending run is finalization in place, on the same run_id. When the record could not be written — the worker swallows exactly that at :770-777 — the two disagree.

Two independent review lanes landed on this same line.

Fix directionDerive recovery from the run's state — succeeded plus terminal finalization pending implies in-place finalization — not from whether a failure record happened to persist.

_begin_progress(finalization_only=True) seeds the registry at finalize (index 7). The shared tail then emits progress_callback("approve") (index 6) whenever the terminal decision is verified_automatic + transition_requested and mutation is allowed. The registry requires strictly increasing stages.

_CaseProgress.advance catches the automation_progress_stage_order raise and _disable("advance") clears the entry. GET /automation loses the case for the rest of a run that is still executing — on the branch whose stated goal is truthful progress.

F6MinorConfirmed ticker_identity_scheduler.py:391

A deliberate policy stop is reported as an execution failure

AutomationTransitionMutationDisabled is raised inside before_write. execute_transition calls before_write() bare (ticker_identity_service.py:385), so it propagates to the loop's generic except Exception at :417, lands in failed_transition_ids, and the tick reports status="partial", reason="transition_execution_failed".

Two ways in: the operator turns off apply profile transitions after the batch was listed, or _mutation_allowed swallows a transient profile-store read error into False. Either way an intentional, correct refusal is recorded as a failure.

Fix directionCatch AutomationTransitionMutationDisabled ahead of the generic handler and count it as a deferral with its own reason.
Refined in round 3 — a pinned contract, not an unowned regression. The current semantics is deliberately fixed by tests/test_ticker_identity_scheduler.py:637, so repairing it changes an intentional contract. And the pinning test is itself the source of the dishonesty: @pytest.mark.parametrize("authority_state", ("disabled", "unavailable")) binds a deliberate policy stop and a transient read failure to the same outcome — two orthogonal axes in one state. The repair must split them, and the parametrized test must split with them.

§ 5

Sequencing: the arming step is the migration, not the canary

Merging on its own is safe, and the reason was traced.

The automation tables are not in the general profile bootstrap — profile_state.py contains no security_lifecycle_automation_runs — and the migration module has zero callers anywhere outside tests/. So on a production profile the tick hits LifecycleAutomationNotInstalled, records automation_schema_absent, and contacts no provider. A partial schema fails closed with LifecycleSchemaMismatch rather than self-completing.

But the shipped default is:

DEFAULT_SECURITY_LIFECYCLE_AUTOMATION_CONFIG = SecurityLifecycleAutomationConfig(
    enabled=True, interval_minutes=5, batch_limit=2, apply_profile_transitions=False,
)

and the parser falls back to those defaults for any absent key, while the tick is already wired into the periodic loop. So the moment the tables exist, unattended lifecycle automation begins on a five-minute cadence — before the single-case canary that is supposed to precede it. apply_profile_transitions=False means no profile mutation, so this is a provider-traffic and sequencing question, not a data-safety one.

Recommended order for Task 13Read-only inventory → authorize the migration and in the same session write security_lifecycle.automation.enabled = false (or change the shipped default to False with a named owner test) → single-case canary → then enable deliberately.
